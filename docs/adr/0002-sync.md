# ADR-0002: Offline-first sync protocol and conflict rules

**Holat:** Qabul qilingan
**Sana:** 2026-09-12

---

## Kontekst

KUNIM ning o'zgarmas tamoyili: **telefondagi SQLite (Drift) = haqiqat manbai**, server = sync +
AI + kontent (`docs/plan.md` Kontekst; `CLAUDE.md` 4-qoida). Foydalanuvchi butun kunni
internetsiz o'tkazishi, ikki qurilmada tahrir qilishi va hech narsa yo'qotmasligi kerak
(2-bosqich DoD: "ikki qurilma offline tahrir → onlayn → yo'qotishsiz").

Shuning uchun sync protokoli **ikki tomon — Flutter `core/sync/` va FastAPI `modules/sync/` —
alohida agentlar tomonidan hech narsani taxmin qilmasdan yozilishi mumkin** darajada aniq
bo'lishi shart. Ushbu ADR shu shartnomani belgilaydi va
`apps/mobile/lib/core/sync/{sync_engine,outbox,conflict}.dart` hamda
`apps/api/app/modules/sync/{router,merge,registry}.py` uchun majburiy spetsifikatsiyadir.

Ikkinchi cheklov: **AI server tomonda foydalanuvchi satrlarini yozmaydi** (`CLAUDE.md` 3-qoida).
Ya'ni sync — foydalanuvchi ma'lumoti uchun **yagona** yozuv yo'li, AI takliflari ham shu yo'ldan
o'tadi.

## Qaror

### 1. Har bir sync jadvalidagi majburiy ustunlar

Sinxronlanadigan jadvallar: `tasks`, `task_categories`, `calendar_events`, `habits`,
`habit_logs`, `goals`, `milestones`, `prayer_logs`, `quran_progress`, `quran_bookmarks`,
`mood_logs`, `sleep_logs`, `health_logs`, `family_logs`, `education_items`, `books`,
`preferences`, `app_limits` (+ upload-only `dw_daily`, `dw_events`, `dw_score`).

| Ustun | Tur | Kim yozadi | Semantika |
|---|---|---|---|
| `id` | UUID **v4** | **KLIENT** | Birlamchi kalit. Klient offline generatsiya qiladi; server yangi `id` bermaydi va klient berganini o'zgartirmaydi. |
| `user_id` | UUID | server tekshiradi | Push'da klient yuborgan `user_id` e'tiborga olinmaydi — server JWT subjektini qo'yadi; mos kelmasa `rejected`. |
| `created_at` | `timestamptz` (UTC) | klient | Qator birinchi yaratilgan payt. Merge'da **ishlatilmaydi**; `created_at > updated_at` bo'lsa server `min()` bilan normallashtiradi. |
| `updated_at` | `timestamptz` (UTC) | klient | **Merge uchun asosiy vaqt muhri.** Klient soati bo'yicha, doim UTC; har lokal yozuvda yangilanadi. |
| `deleted_at` | `timestamptz` (UTC), nullable | klient | Soft delete. `NULL` = tirik. Hard delete na klientda, na serverda qilinmaydi — faqat tombstone tozalash job'ida. |
| `server_version` | `BIGINT` | **FAQAT SERVER** | Foydalanuvchi bo'yicha **monoton o'suvchi** raqam; pull kursori shu ustun bo'yicha. Klient uni hisoblamaydi, faqat serverdan kelganini saqlaydi. Yangi satrda `0`. |
| `dirty` | `BOOL` | faqat klient | "Bu qatorda push qilinmagan o'zgarish bor". **Serverga hech qachon yuborilmaydi**; server sxemasida bu ustun yo'q. |

Qo'shimcha qoidalar:

- Barcha vaqt muhrlari **UTC**, RFC 3339, `Z` qo'shimchasi bilan, **millisekund aniqlik**
  (`2026-09-12T08:15:30.123Z`). Lokal vaqt zonasi faqat UI da.
- Server tomonda bu ustunlar `db/mixins.py` (`UUIDPk`, `Timestamps`, `SoftDelete`, `Versioned`)
  orqali beriladi; yangi sync jadval mixin'siz yaratilmaydi.
- `(user_id, server_version)` unikal bo'lishi va pull `ORDER BY server_version ASC` bilan
  barqaror sahifalanishi shart.

### 2. Outbox (faqat klientda)

```
sync_outbox(
  seq        INTEGER PRIMARY KEY AUTOINCREMENT,  -- push tartibi, klient ichida global
  entity     TEXT NOT NULL,          -- jadval nomi, masalan 'tasks'
  row_id     TEXT NOT NULL,          -- UUIDv4
  op         TEXT NOT NULL,          -- 'upsert' | 'delete'
  payload    TEXT NOT NULL,          -- JSON: qatorning to'liq holati (dirty'siz)
  attempts   INTEGER NOT NULL DEFAULT 0,
  last_error TEXT
)
```

**Invariant (buzilmaydi): lokal satr yozuvi + outbox yozuvi — BITTA tranzaksiyada.**
Repository hech qachon qatorni outbox yozuvisiz yozmaydi (`CLAUDE.md` 2-qoida). Biri
muvaffaqiyatsiz bo'lsa — ikkalasi rollback.

- Yagona texnik yo'l: `core/db/base_repository.dart` dagi `writeWithOutbox<T>()`. Feature
  repository'lari `into(table).insert/update/delete` ni to'g'ridan-to'g'ri chaqirmaydi; buni
  lint qoidasi va `apps/mobile/test/sync/outbox_invariant_test.dart` tekshiradi.
- **Koalessiya:** push oldidan bitta `(entity, row_id)` uchun faqat eng katta `seq` li yozuv
  yuboriladi; orada `delete` bo'lsa va undan keyin `upsert` bo'lmasa — `delete` g'olib.
  Qolgan `seq` lar batch muvaffaqiyatli bo'lganda o'chiriladi.
- `SyncEngine` trigger'lari: app resume, internet qaytdi, foreground'da har 5 daqiqa, N=20 lokal
  yozuvdan keyin, pull-to-refresh, silent data-push. Bir vaqtda **bitta** sync sessiyasi
  (mutex) — parallel push/pull taqiqlanadi.
- `attempts` eksponensial backoff (1s, 2s, 4s … max 15 daq). `attempts >= 10` bo'lganda yozuv
  outbox'da **qoladi**, `last_error` saqlanadi va Sozlamalar → Diagnostika ekranida
  ko'rsatiladi — **hech qachon jimgina tashlab yuborilmaydi**. `last_error` ga shaxsiy
  ma'lumot yozilmaydi.

### 3. Wire kontrakt

#### `POST /sync/push`

```jsonc
// Request
{
  "device_id": "9f0e...",              // qurilma identifikatori (UUIDv4)
  "batch_id":  "1c1f...",              // UUIDv4, KLIENT generatsiya qiladi = idempotentlik kaliti
  "changes": [                         // <= 200 element, outbox seq tartibida
    {
      "client_seq": 128,               // sync_outbox.seq — javobni moslashtirish uchun
      "entity":  "tasks",
      "row_id":  "6b1d...",            // UUIDv4, payload.id ga teng
      "op":      "upsert",             // "upsert" | "delete"
      "base_version": 41,              // klient bilgan oxirgi server_version (yangi satrda 0)
      "payload": { "id": "6b1d...", "updated_at": "2026-09-12T08:30:00.000Z", "...": "..." }
    }
  ]
}

// Response 200
{
  "batch_id": "1c1f...",
  "server_time": "2026-09-12T08:30:01.000Z",
  "max_server_version": 10428,
  "results": [
    { "client_seq": 128, "row_id": "6b1d...", "entity": "tasks",
      "status": "applied",  "server_version": 10427 },
    { "client_seq": 129, "row_id": "77aa...", "entity": "habit_logs",
      "status": "conflict", "server_version": 10428, "server_row": { "...": "..." } },
    { "client_seq": 130, "row_id": "88bb...", "entity": "tasks",
      "status": "rejected", "reason": "updated_at_in_future" }
  ]
}
```

- Har o'zgarish uchun status **aniq** `applied | conflict | rejected` dan biri.

| Status | Ma'nosi | Klient nima qiladi |
|---|---|---|
| `applied` | Serverdagi holat klient yuborganidek. | Qatorga `server_version` ni yozadi, `dirty = 0`, outbox yozuvini o'chiradi. |
| `conflict` | Merge natijasi klient yuborganidan farq qiladi; javobda **to'liq** `server_row`. | Lokal qatorni `server_row` bilan **to'liq almashtiradi**, `dirty = 0`, outbox yozuvini o'chiradi, **qayta yubormaydi**. |
| `rejected` | Qabul qilinmadi va shu holicha qabul qilinmaydi. `reason` majburiy. | `reason` bo'yicha harakat qiladi (quyida). |

`rejected` sabablari — **yopiq ro'yxat**:

| `reason` | Sabab | Klient harakati |
|---|---|---|
| `updated_at_in_future` | `updated_at > server_time + 24 soat` | Qatorni `updated_at = now()` bilan **qayta muhrlaydi**, `attempts++`, outbox'ga qaytadan qo'yadi. |
| `schema_invalid` | Payload sxemaga mos emas | Outbox'da `last_error` bilan qoldiradi, diagnostikaga chiqaradi, qayta yubormaydi. |
| `unknown_entity` | `entity` `SYNC_ENTITIES` da yo'q | Outbox yozuvini o'chiradi (eski klient qoldig'i), loglaydi. |
| `readonly_entity` | Entity faqat-onlayn yoki pull-only (`content`, Qur'on, preset) | Outbox yozuvini o'chiradi; bu klient bug'i → Sentry. |
| `foreign_user` | `payload.user_id` JWT subjektiga mos emas | Outbox yozuvini o'chiradi, sessiyani qayta tekshiradi. |
| `payload_too_large` | Bitta `payload` > 64 KB | Diagnostikaga chiqaradi. |

**Chegaralar:** `changes` ≤ **200** (ortiq bo'lsa HTTP 400 `batch_too_large`), bitta `payload`
≤ 64 KB, butun tana ≤ 4 MB. `batch_id` UUIDv4 bo'lmasa → HTTP 400.

**Tranzaksiya chegarasi:** butun batch bitta ochiq tranzaksiyada, lekin **har bir change
alohida SAVEPOINT ichida** qo'llanadi — bitta `rejected` boshqalarini bekor qilmaydi.
`sync_batches` yozuvi va natijalar o'sha tranzaksiyada commit qilinadi, ya'ni saqlangan javob
har doim haqiqiy holatga mos.

**Idempotentlik:**

```
sync_batches(batch_id UUID PK, user_id, device_id, request_hash TEXT, response JSONB, created_at)
```

- Bir xil `batch_id` + bir xil `request_hash` (changes[] ning kanonik JSON sha256) → server
  **saqlangan javobni qaytaradi va o'zgarishlarni QAYTA QO'LLAMAYDI**.
- Bir xil `batch_id` + **boshqa** `request_hash` → HTTP 409 `{"code": "batch_id_reused"}`;
  klient yangi `batch_id` bilan qayta yuboradi.
- Saqlash muddati **7 kun**; undan eski `batch_id` qaytadan kelsa yangi batch sifatida qabul
  qilinadi — bu xavfsiz, chunki har change `id` bo'yicha upsert va merge qoidalari idempotent.

#### `GET /sync/pull?cursor=&limit=500&entities=`

```jsonc
// Response 200
{
  "rows": [
    { "entity": "tasks", "server_version": 10427,
      "row": { "id": "...", "deleted_at": null, "...": "..." } },
    { "entity": "tasks", "server_version": 10430,
      "row": { "id": "...", "deleted_at": "2026-09-10T12:00:00.000Z" } }
  ],
  "next_cursor": 10430,
  "has_more": false,
  "full_resync_required": false,
  "server_time": "2026-09-12T08:30:01.000Z"
}
```

- `server_version > cursor` bo'lgan qatorlar, `server_version ASC` tartibida; `limit` default va
  maksimum **500** (kattaroq so'ralsa 500 ga qisqartiriladi). `entities` — ixtiyoriy filtr.
- **`server_version` semantikasi:** foydalanuvchi bo'yicha monoton hisoblagich, **global
  sequence emas**. Har yozuv tranzaksiyasi ichida
  `UPDATE sync_user_state SET last_version = last_version + 1 WHERE user_id = :u RETURNING last_version`.
  Satr qulfi yozuvlarni serializatsiya qiladi va **bo'shliqsiz, commit tartibiga mos**
  ketma-ketlikni beradi.
  > Global `BIGSERIAL` **ishlatilmaydi**: u raqamni tranzaksiya boshida ajratadi, commit tartibi
  > esa boshqacha bo'lishi mumkin → kursor qatorni sakrab o'tishi mumkin edi.
- **Tombstone'lar qaytariladi** (`deleted_at != null`) — klient ularni lokal o'chirish uchun
  ishlatadi. **Istisno:** `cursor = 0` bo'lganda tombstone'lar yuborilmaydi — yangi qurilmada
  o'chiriladigan narsa yo'q va bu birinchi yuklash trafigini kamaytiradi.
- **Yangi qurilma `cursor = 0` dan boshlaydi** va butun holatni sahifama-sahifa oladi.
  Kursor `sync_state(user_id, cursor, last_pull_at)` da saqlanadi; klient `next_cursor` ni
  **faqat butun sahifa lokal tranzaksiyada muvaffaqiyatli qo'llangandan keyin** yozadi.
  `has_more = true` bo'lsa darhol keyingi sahifa so'raladi.
- Pull o'z qurilmasi yozuvlarini ham qaytaradi (echo); klient `server_version` bo'yicha
  idempotent qo'llaydi.
- Push'dan keyin klient **majburiy** pull qiladi; aks holda o'zini sinxron deb hisoblamaydi.

### 4. Saqlash muddatlari va tiklash

- **Tombstone: 90 kun.** `jobs/cleanup.py` 90 kundan eski, `deleted_at` qo'yilgan qatorlarni
  jismonan o'chiradi va o'sha paytdagi eng katta `server_version` ni
  `sync_user_state.purged_up_to_version` ga yozadi.
- **Kursor purge oynasidan eski bo'lsa** (`cursor < purged_up_to_version`) server javobda
  **`full_resync_required: true`** qaytaradi, `rows` bo'sh bo'ladi. Klient majburiy to'liq
  resync qiladi:
  1. `sync_outbox` **saqlanadi** (yuborilmagan lokal o'zgarishlar yo'qolmaydi);
  2. sync jadvallaridagi `dirty = 0` qatorlar o'chiriladi (`dirty = 1` qatorlar qoladi — ular
     hali serverga yetmagan);
  3. `cursor = 0` qilinadi va to'liq pull bajariladi;
  4. pull tugagach outbox odatdagidek push qilinadi.

  **Qisman tiklash taqiqlanadi** — u jimgina ma'lumot yo'qotishga olib keladi.
- **`row_history` — 30 kun.** Server har qabul qilingan o'zgarishning oldingi va yangi holatini
  `row_history(entity, row_id, user_id, before jsonb, after jsonb, server_version, device_id,
  created_at)` ga yozadi. Bu **faqat support orqali qo'lda tiklash** uchun; klient endpoint'i
  uni o'qimaydi, MVP da avtomatik rollback yo'q. Kirish `/admin` orqali va `audit_logs` bilan
  yozib boriladi. `EncryptedText` ustunlari bu yerda ham shifrlangan saqlanadi.
- **`sync_batches` — 7 kun** (yuqorida). Keshlangan javobdagi `server_row` ichidagi `EncryptedText` ustunlari shifrlangan saqlanadi va replay'da ochiladi — replay javobi asl javob bilan bayt-ma-bayt bir xil; buzilgan shifrmatn replay'ni jimgina emas, xato bilan to'xtatadi.
- **Loglar:** rad etilgan yoki muvaffaqiyatsiz change uchun faqat entity, `row_id`, maydon nomlari va xato kodlari loglanadi — yuborilgan qiymatlar, exception matni va SQL parametrlari hech qachon.

## Konflikt matritsasi (normativ)

Default: **row-level last-write-wins `updated_at` bo'yicha**. Merge **faqat serverda** —
`apps/api/app/modules/sync/merge.py`. Klientdagi `core/sync/conflict.dart` merge qoidalarini
takrorlamaydi; u faqat server javobini qo'llaydi (status ishlash, `server_row` bilan
almashtirish, `updated_at_in_future` da qayta muhrlash). **Sabab:** Dart va Python'dagi ikki
merge implementatsiyasi muqarrar ravishda jimgina ajralib ketadi.

| # | Doira | Qoida | Natija |
|---|---|---|---|
| 1 | Barcha sync jadvallari (default) | Kelayotgan `updated_at` > mavjud → klient g'olib | `applied` |
| 2 | Default, teskari | Kelayotgan `updated_at` < mavjud → server g'olib, `server_row` qaytadi | `conflict` |
| 3 | Default, teng `updated_at`, payload aynan bir xil | No-op | `applied` |
| 4 | Default, teng `updated_at`, payload farqli | **Serverda saqlangan holat g'olib** (deterministik tie-break) | `conflict` |
| 5 | Soft delete | Merge natijasida `deleted_at > updated_at` bo'lsa **o'chirish g'olib** — LWW dan qat'i nazar. Tiriltirish faqat `updated_at > deleted_at` bo'lgan keyingi `upsert` bilan | `applied`/`conflict` |
| 6 | Har qanday qator, `updated_at > server_time + 24h` | **`rejected`**, `reason: "updated_at_in_future"` | Klient `now()` bilan qayta muhrlaydi va qaytadan yuboradi |
| 7 | `created_at > updated_at` | Server `created_at = min(mavjud, kelayotgan)` qilib normallashtiradi, rad etmaydi | `applied` |
| 8 | `tasks.completed_at` | **max-wins** (`NULL` eng kichik). Sync hech qachon vazifani "bajarilmagan" holatga qaytarmaydi. Qolgan maydonlar LWW. `completed` bayrog'i sinxronlanmaydi — `completed_at IS NOT NULL` dan hosil qilinadi | `applied`/`conflict` |
| 9 | `habit_logs` | Natural kalit **`(user_id, habit_id, date)`**. Additiv sonli maydonlar `count`, `value` → **max-wins**; `note` LWW | `conflict` |
| 26 | `daily_scores` | NK **`(user_id, date)`**. `points`, `done`, `planned` — **max-wins**: ikki qurilma kunning bir qismini ko'rgan bo'lishi mumkin, ko'proq ish ko'rgani haq. Ball qurilmada hisoblanadi (`features/stats/domain/daily_score.dart`), server faqat saqlaydi va reyting uchun qo'shadi | `conflict` |
| 10 | `prayer_logs` | NK **`(user_id, prayer_key, date)`**. `status` — **tartiblangan enum max-wins**: `none(0) < qaza(1) < alone(2) < jamaah(3)`; `note` LWW | `conflict` |
| 11 | `mood_logs` | NK **`(user_id, coalesce(ref_id,''), date)`**. `score` LWW (additiv emas), `note` LWW, `tags` — ikki to'plamning **birlashmasi**, ko'pi bilan **32** element (jadval ostidagi izoh) | `conflict` |
| 12 | `sleep_logs` | NK **`(user_id, coalesce(ref_id,''), date)`**. `bed_time`/`wake_time` LWW **juftlik sifatida** (ikkalasi bitta yutuvchidan); `duration_min` — hosil qiluvchi, max-wins **emas**; `quality` LWW, `note` LWW | `conflict` |
| 13 | `health_logs` | NK **`(user_id, coalesce(ref_id,''), date)`**. Additiv: `water_ml`, `steps`, `workout_min`, `calories` → **max-wins**. Additiv emas: `weight_kg` → LWW; `note` LWW | `conflict` |
| 14 | **NK to'qnashuvi** (9–13, 25) | Ikki qurilma bir xil natural kalit uchun **turli `id`** yaratsa: `created_at` kichikrog'i (teng bo'lsa leksikografik kichik `id`) omon qoladi, maydonlar 9–13 va 25 bo'yicha birlashtiriladi; yutqazgan `id` tombstone qilinadi va payload'iga `{"merged_into": "<omon qolgan id>"}` qo'shiladi. Klient ikkala qatorni ham qabul qiladi va `merged_into` tombstone'ini UI da ko'rsatmaydi | `conflict` |
| 15 | `quran_progress` | Foydalanuvchi uchun **bitta qator** (NK `(user_id)`). `last_ayah_key` — **LWW** | `conflict` |
| 16 | `quran_progress.pages_read_total`, `ayahs_read_total`, `khatm_count` | **max-wins** — umumiy hisob kamaymaydi | `conflict` |
| 17 | `quran_bookmarks` | Oddiy LWW + soft delete (1–5) | — |
| 18 | `goals`, `milestones` | LWW; `progress_percent` max-wins **emas** (maqsad orqaga ham qaytishi mumkin) | — |
| 19 | `preferences` | Foydalanuvchi uchun bitta qator; **butun qator LWW** (maydonli merge yo'q) | — |
| 20 | `task_categories`, `calendar_events`, `habits`, `education_items`, `books`, `app_limits` | LWW + soft delete | — |
| 21 | `dw_daily`, `dw_score` | **Upload-only.** NK `(user_id, date, app_key)` / `(user_id, date)`; `minutes`, `sessions`, `waste_minutes_est`, `score` → **max-wins**. Pull bu qatorlarni hech qachon qaytarmaydi | `applied` |
| 22 | `dw_events` | **Upload-only, append-only**; `id` bo'yicha idempotent insert, hech qachon `conflict` bermaydi | `applied` |
| 23 | Noma'lum `entity`, yoki JWT `user_id` ga mos kelmagan qator | **`rejected`** (`unknown_entity` / `foreign_user`) | Klient yozuvni outbox'dan olib tashlaydi va loglaydi |
| 24 | `content`, Qur'on matni, namoz preset'lari | **Pull-only kesh**; push qilinsa rad etiladi | `rejected` (`readonly_entity`) |
| 25 | `family_logs` | NK **`(user_id, coalesce(ref_id,''), date)`**. Additiv: `minutes` → **max-wins**; `activities` — ikki to'plamning **birlashmasi**, ko'pi bilan **32** element (11-qatordagi kesish qoidasi); `note` LWW. NK to'qnashuvi 14-qoida bo'yicha. *(2026-09-14 da qo'shildi; 1–24 raqamlari o'zgarmadi)* | `conflict` |

**To'plam birlashmasi (11 va 25-qatorlar) semantikasi.** Elementlar `(tur, matn)` bo'yicha takrorlanmaydi. Birlashma limit ichida bo'lsa (`mood_logs.tags` va `family_logs.activities` uchun **32** — wire sxemasidagi ro'yxat limiti bilan bir xil) natija **saralangan** holda qaytadi, shuning uchun ikkala qurilma bir xil natijaga keladi. Limitdan oshsa kesish deterministik: avval LWW **g'olibining** elementlari (g'olib ro'yxatidagi tartibda), keyin **yutqazganning** qolgan elementlari (o'sha saralangan tartibda), so'ng birinchi 32 tasi qoldiriladi va **natija yana saralanadi** (limit ichidagi birlashma bilan bir xil ko'rinish; shu tufayli saqlangan ro'yxatni o'zi bilan qayta birlashtirish hech narsani o'zgartirmaydi va o'zgarmagan qayta push `conflict` bermaydi). Wire'dan kelgan g'olib ro'yxati ≤ 32 bo'lgani uchun u hech qachon kesilmaydi va birlashtirilgan qator har doim sxema validatsiyasidan qayta o'tadi. Limit merge siyosatining xossasi (`FieldRule.max_items`, `merge.py`), servisdagi maxsus holat emas.

**Test majburiyati:** `apps/api/tests/sync/test_merge_matrix.py` yuqoridagi **har bir qator**
uchun kamida bitta kazus saqlaydi va test nomi qator raqamini o'z ichiga oladi
(`test_rule_09_habit_logs_natural_key_max_wins`). `merge.py` dagi har bir qoida kod izohida
mos qator raqamini ko'rsatadi. `apps/mobile/test/sync/` ikki in-memory Drift baza + test API
bilan uchidan-uchiga ssenariylarni tekshiradi (2-bosqich DoD).

## Jadval tasnifi

| Offline (ikki tomonlama sync) | Faqat onlayn | Faqat lokal (hech qachon yuklanmaydi) |
|---|---|---|
| `tasks`, `task_categories`, `calendar_events`, `habits`, `habit_logs`, `goals`, `milestones`, `prayer_logs`, `quran_progress`, `quran_bookmarks`, `mood_logs`, `sleep_logs`, `health_logs`, `family_logs`, `education_items`, `books`, `preferences`, `app_limits` | `auth` / `refresh_tokens`, avatar yuklash, AI chat / planner / reschedule / recommendations / memory (`ai_proposals`, `ai_messages`, `ai_memory`), server statistikasi, `/admin` | xom `dw_sessions`, `usage_sessions_raw`, `scrolling_events`, xom `notification_events`, AI javob keshi |
| `dw_daily`, `dw_events`, `dw_score` — **faqat yuklash (upload-only)** | | |
| `content` (hikmatlar), Qur'on matni (bundled), namoz preset'lari — **faqat o'qish (pull-only)** | | |

- `SYNC_ENTITIES` — serverdagi **yagona** ro'yxat (`app/modules/sync/registry.py`); u ham
  `/sync/push` validatsiyasi, ham OpenAPI generatsiyasi uchun manba. Ro'yxatda yo'q entity →
  `rejected` / `unknown_entity`.
- Upload-only entity pull javobida umuman chiqmaydi; pull-only entity'ga push → `rejected` /
  `readonly_entity`.
- Qurilmalar aro ephemer holat ("oxirgi ko'rilgan ekran") sync qilinmaydi.

## AI invarianti

**Server AI nomidan foydalanuvchi qatorlarini yozmaydi** (`CLAUDE.md` 3-qoida). Sync uchun bu
quyidagini anglatadi:

1. AI agentlari faqat `ai_proposals(agent, payload jsonb, status, applied_diff)` yaratadi.
   `ai_proposals` — **faqat onlayn** jadval, sync entity emas.
2. `tasks`, `calendar_events` va boshqa sync jadvallariga yozuv **faqat** `/sync/push` orqali
   keladi. `app/ai/**` ichida sync model'lariga `INSERT`/`UPDATE`/`DELETE` bo'lmasligi statik
   test bilan tekshiriladi (`tests/ai/test_ai_never_writes_user_rows.py`).
3. Foydalanuvchi taklifni qabul qilganda klient diff'ni **lokal** qo'llaydi (qator + outbox
   bitta tranzaksiyada), keyin odatdagi push bajariladi. Server faqat `ai_proposals.status` ni
   `accepted` / `modified` / `rejected` ga o'tkazadi va `applied_diff` ni saqlaydi.
4. Natijada taklif **offline'da ham** qabul qilinishi va keyinroq sinxronlanishi mumkin;
   offline invariantlar buzilmaydi va yozuv yo'li bitta bo'lib qoladi.

## Sabablar

- **Klientda UUIDv4** — offline yaratilgan qator darhol lokal bog'lanishlarga (`task_id`,
  `habit_id`) kerak; server ID kutish offline-first ni buzardi.
- **Outbox + bitta tranzaksiya** — "yozildi, lekin yuborilmadi" holatini strukturaviy ravishda
  imkonsiz qiladi; bu offline-first tizimlarda ma'lumot yo'qotishning eng keng tarqalgan sababi.
- **Foydalanuvchi bo'yicha monoton `server_version`** — qurilma soatining noto'g'riligi kursorga
  ta'sir qilmaydi (faqat merge'ga, 6-qoida bilan cheklangan); kursor bo'shliqsiz.
- **`batch_id` idempotentligi** — tarmoq uzilganda takroriy push xavfsiz; "duplikat vazifa"
  sinfi butunlay yopiladi.
- **Serverda yagona merge** — ikki implementatsiyaning jimgina ajralishi sinxronizatsiyadagi
  eng qimmat bug turi; deterministik merge esa avtomatik matritsa testini mumkin qiladi.
- **90 kunlik tombstone + majburiy to'liq resync** — cheksiz tombstone o'sishi bilan uzoq
  offline qurilmaning to'g'ri ishlashi o'rtasidagi muvozanat.
- **Additiv maydonlarda max-wins** — "suv ichdim", "namoz o'qidim" kabi yozuvlarni boshqa
  qurilmaning eski nusxasi bekor qila olmasligi kerak.

## Oqibatlar

### Ijobiy

- Klient offline to'liq ishlaydi; internet paydo bo'lganda outbox `seq` tartibida yuboriladi.
- Takroriy push xavfsiz — mobil tarmoq uchun kritik.
- Merge deterministik → 2-bosqich DoD dagi "konflikt matritsasi avtomatik test" yozilishi mumkin.
- `row_history` support'ga tasodifiy o'chirishlarni tiklash imkonini beradi.
- AI taklifi ham oddiy offline yozuvga aylanadi — bitta kod yo'li, bitta test to'plami.
- Kontrakt shu darajada aniqki, klient va server alohida agentlar tomonidan parallel yozilishi
  mumkin.

### Salbiy

- LWW ma'lumot yo'qotishi mumkin: bir vaqtda ikki qurilmada tahrir qilinganda yutqazgan tahrir
  UI dan yo'qoladi (`row_history` da 30 kun qoladi). Bu ongli savdo.
- `server_version` ni satr qulfi bilan ajratish foydalanuvchi bo'yicha yozuvlarni
  serializatsiya qiladi — bitta foydalanuvchi uchun push o'tkazuvchanligi cheklanadi (amalda
  muammo emas).
- To'liq resync 90 kundan ortiq offline qolgan qurilmada bir necha MB trafik.
- NK merge (14-qoida) klientda ikkita qatorni qabul qilishni talab qiladi; UI `merged_into`
  tombstone'ini ko'rsatmasligi kerak.
- `sync_batches` va `row_history` server bazasini o'stiradi; `cleanup` job majburiy va uning
  ishlamay qolishi alert qilinadi.

## Amalga oshirish uchun majburiy qoidalar

1. **Lokal qator yozuvi + `sync_outbox` insert — har doim bitta Drift tranzaksiyasida**, yagona
   yo'l `writeWithOutbox<T>()`. Boshqa yo'l bilan yozgan kod ko'rib chiqishda rad etiladi.
2. Barcha sync qator ID'lari klientda **UUIDv4**; server ID generatsiya qilmaydi va klient
   berganini o'zgartirmaydi.
3. Har sync jadvalida §1 dagi yettita ustun bo'lishi shart (`db/mixins.py` orqali);
   `(user_id, server_version)` unikal. Migratsiya buni buzsa CI test yiqiladi.
4. `user_id` **faqat** JWT subjektidan olinadi; payload'dagi mos kelmasa → `foreign_user`.
5. Push batch ≤ **200**, pull `limit` ≤ **500**. Klient chegaralarni `GET /sync/limits` dan
   oladi, lokal default sifatida 200/500 ishlatadi.
6. `batch_id` har batch uchun yangi UUIDv4; **qayta yuborishda o'sha** `batch_id` ishlatiladi.
7. Klient `next_cursor` ni faqat sahifa to'liq lokal tranzaksiyada qo'llangandan keyin yozadi.
8. Klientda **merge mantiqi yo'q**: `conflict` javobidagi `server_row` shartsiz qabul qilinadi
   va lokal qatorni to'liq almashtiradi. `conflict.dart` faqat status/qayta muhrlash mantiqini
   saqlaydi.
9. `full_resync_required: true` → majburiy to'liq resync (§4 dagi 4 qadam). Qisman tiklash
   taqiqlanadi.
10. `merge.py` dagi har qoida konflikt matritsasi qator raqamini izohda ko'rsatadi va
    `test_merge_matrix.py` da mos testga ega bo'ladi.
11. `cleanup` job kunlik: tombstone 90 kun, `row_history` 30 kun, `sync_batches` 7 kun.
    Muvaffaqiyatsiz bo'lsa alert.
12. **AI xizmati sync jadvallariga yozmaydi**; statik test bilan tekshiriladi.
13. Barcha timestamp'lar UTC, RFC 3339, millisekund aniqlik.
14. Upload-only (`dw_*`) va pull-only (`content`, Qur'on, preset) entity'lar uchun noto'g'ri
    yo'nalishdagi so'rov `rejected` / `readonly_entity` bilan javob beradi.
15. Bir vaqtda bitta sync sessiyasi (mutex); parallel push/pull taqiqlanadi.
16. Har log jadvali o'z `ref_id` ma'nosini (`habit_id`, `prayer_key`, …) migratsiya izohida
    hujjatlaydi — NK noaniq qolmaydi.

## Rejada aniqlanmagan — shu yerda hal qilindi

| Savol | Qaror |
|---|---|
| `server_version` qanday ajratiladi | `sync_user_state.last_version` — foydalanuvchi bo'yicha monoton hisoblagich, yozuv tranzaksiyasi ichida satr qulfi bilan. Global `BIGSERIAL` rad etildi. |
| Teng `updated_at` da kim g'olib | Payload bir xil → no-op (`applied`); farqli → **server g'olib** (`conflict`). |
| `base_version` ning roli | Faqat diagnostika/maslahat; qaror LWW va merge qoidalariga tayanadi. |
| Batch qisman muvaffaqiyatsizligi | Har change alohida SAVEPOINT; bitta `rejected` butun batch'ni bekor qilmaydi. |
| `conflict` da server qatori qaytadimi | Ha — `server_row`. Aks holda klient darhol pull qilishga majbur bo'lardi. |
| Javobni change'ga moslashtirish | `client_seq` (= `sync_outbox.seq`) so'rov va javobda uzatiladi. |
| `sync_batches` saqlash muddati | 7 kun (klient retry oynasidan ancha uzun). |
| `batch_id` boshqa payload bilan qayta ishlatilishi | HTTP 409 `batch_id_reused`. |
| `cursor = 0` da tombstone'lar | Yuborilmaydi; `cursor > 0` da yuboriladi. |
| Purge oynasidan eski kursor mexanizmi | `sync_user_state.purged_up_to_version` + `full_resync_required: true` + 4 qadamli resync; `dirty` qatorlar va outbox saqlanadi. |
| NK to'qnashuvi (turli `id`) | `created_at` kichikrog'i omon qoladi (teng bo'lsa leksikografik kichik `id`); yutqazgan `merged_into` tombstone'i bo'ladi. |
| `prayer_logs.status` tartibi | `none(0) < qaza(1) < alone(2) < jamaah(3)`, max-wins. |
| Qaysi maydonlar "additiv" | `health_logs`: `water_ml`, `steps`, `workout_min`, `calories`; `habit_logs`: `count`, `value`; `quran_progress`: `pages_read_total`, `ayahs_read_total`, `khatm_count`; `family_logs`: `minutes`. Qolganlari LWW — `sleep_logs.duration_min` va `goals.progress_percent` max-wins **emas**. |
| Log jadvallarida `ref_id` semantikasi | Har jadval o'z ma'nosini migratsiyada hujjatlaydi; bo'sh bo'lsa NK da `coalesce(ref_id, '')`. |
| `preferences` merge darajasi | Butun qator LWW (maydonli merge yo'q). |
| Outbox koalessiyasi | Batch ichida `(entity,row_id)` bo'yicha oxirgi `seq`; `delete` oldingi `upsert` larni bosadi. |
| Outbox muvaffaqiyatsizlik chegarasi | 10 urinish → diagnostika ekrani; hech qachon jimgina o'chirilmaydi. |
| Payload hajmi chegarasi | Bitta change ≤ 64 KB, tana ≤ 4 MB. |
| `tasks.completed` bayrog'i | Sinxronlanmaydi; `completed_at IS NOT NULL` dan hosil qilinadi. |
| `dw_events` konflikti | Append-only, `id` bo'yicha idempotent insert; hech qachon `conflict` bermaydi. |
| `rejected` sabablari ro'yxati | Yopiq enum: `updated_at_in_future`, `schema_invalid`, `unknown_entity`, `readonly_entity`, `foreign_user`, `payload_too_large`. |
| Merge qayerda yashaydi | **Faqat serverda.** `conflict.dart` merge qoidalarini takrorlamaydi. |
| Push va pull parallelligi | Taqiqlanadi; bitta sync mutex. |

## Qachon qayta ko'riladi

1. Konflikt matritsasi testida (2-bosqich) LWW bilan tuzatib bo'lmaydigan ma'lumot yo'qotish
   ssenariysi topilsa;
2. Foydalanuvchilarning ≥ 1% ida bitta sync sikli doimiy 200 dan ortiq o'zgarish hosil qilsa
   (batch limiti yoki delta format qayta ko'riladi);
3. Family Account (2-bosqich) bir qatorni **bir nechta foydalanuvchi** tahrir qiladigan holatni
   kiritsa — per-user `server_version` va LWW yetarli bo'lmaydi;
4. Pull p95 kechikishi 500 qatorli sahifada > 1 s bo'lsa, yoki `sync_user_state` satr qulfi
   push p95 ni > 500 ms qilsa;
5. `full_resync_required` oyiga faol qurilmalarning 1% dan ko'pida ishga tushsa (tombstone
   muddati uzaytiriladi).
