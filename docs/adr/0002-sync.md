# ADR-0002: Offline-first sync protocol and conflict rules

## Status

Accepted — 2026-09-12

## Context

KUNIM ning o'zgarmas tamoyili: **telefondagi SQLite = haqiqat manbai**, server = sync + AI +
kontent (`docs/plan.md`, Kontekst; `CLAUDE.md`, 4-qoida). Foydalanuvchi butun kunni internetsiz
o'tkazishi, ikki qurilmada tahrir qilishi va hech narsa yo'qotmasligi kerak (2-bosqich DoD:
"ikki qurilma offline tahrir → onlayn → yo'qotishsiz").

Shu sababli sync protokoli **ikki tomon (Flutter `core/sync/` va FastAPI `modules/sync/`)
alohida agentlar tomonidan taxmin qilmasdan yozilishi mumkin** darajada aniq bo'lishi shart.
Ushbu ADR shu shartnomani belgilaydi va `apps/mobile/lib/core/sync/sync_engine.dart` hamda
`apps/api/app/modules/sync/{router.py,merge.py}` uchun majburiy spetsifikatsiyadir.

## Decision

### 1. Required columns on every syncable table

Har bir sinxronlanadigan jadval (`tasks`, `task_categories`, `calendar_events`, `habits`,
`habit_logs`, `goals`, `milestones`, `prayer_logs`, `quran_progress`, `quran_bookmarks`,
`mood_logs`, `sleep_logs`, `health_logs`, `education_items`, `books`, `preferences`,
`app_limits`, `dw_daily`) quyidagi ustunlarga **MUST** ega bo'lsin:

| Ustun | Tur | Kim yozadi | Semantika |
|---|---|---|---|
| `id` | UUID **v4** | **KLIENT** | Birlamchi kalit. Klient offline generatsiya qiladi; server yangi `id` bermaydi va klient berganini o'zgartirMAYDI. |
| `user_id` | UUID | server tekshiradi | Egalik. Push'da klient yuborgan `user_id` e'tiborga olinMAYDI — server JWT subjektini qo'yadi; mos kelmasa `rejected`. |
| `created_at` | timestamptz (UTC) | klient | Qator birinchi marta yaratilgan payt. Merge'da ishlatilMAYDI; faqat ko'rsatish va tartib uchun. |
| `updated_at` | timestamptz (UTC) | klient | **Merge uchun asosiy vaqt muhri.** Klient soati bo'yicha, doim UTC; har lokal yozuvda yangilanadi. |
| `deleted_at` | timestamptz (UTC), nullable | klient | Soft delete. `NULL` = tirik. Hard delete na klientda, na serverda qilinMAYDI (faqat tombstone tozalash jobi). |
| `server_version` | BIGINT | **FAQAT SERVER** | Har foydalanuvchi uchun **monoton o'suvchi** raqam; server har qabul qilingan o'zgarishda per-user hisoblagichdan yangi qiymat beradi. Pull kursori shu ustun bo'yicha. Klient uni o'zi hisoblaMAYDI, faqat serverdan kelganini saqlaydi. |
| `dirty` | BOOL | faqat klient | Lokal bayroq: "bu qatorda push qilinmagan o'zgarish bor". **Serverga hech qachon yuborilMAYDI**; server sxemasida bu ustun yo'q. |

Qo'shimcha qoidalar:

- Barcha vaqt muhrlari **UTC**; lokal vaqt zonasi faqat UI da qo'llanadi.
- Server tomonda bu ustunlar `db/mixins.py` (`UUIDPk`, `Timestamps`, `SoftDelete`, `Versioned`)
  orqali beriladi; yangi sync jadval mixin'siz yaratilMASIN.
- `(user_id, server_version)` unikal bo'lishi va pull `ORDER BY server_version ASC` bilan
  barqaror sahifalanishi shart.

### 2. Outbox (client only)

```
sync_outbox(
  seq        INTEGER PRIMARY KEY AUTOINCREMENT,  -- push tartibi
  entity     TEXT NOT NULL,          -- jadval nomi, masalan 'tasks'
  row_id     TEXT NOT NULL,          -- UUIDv4
  op         TEXT NOT NULL,          -- 'upsert' | 'delete'
  payload    TEXT NOT NULL,          -- JSON: qatorning to'liq holati (dirty'siz)
  attempts   INTEGER NOT NULL DEFAULT 0,
  last_error TEXT
)
```

**Invariant (buzilmaydi): row write + outbox write — BITTA tranzaksiyada.**
Repository hech qachon qatorni outbox yozuvisiz yozMAYDI (`CLAUDE.md`, 2-qoida). Ikkalasi bitta
Drift tranzaksiyasida bajariladi; biri muvaffaqiyatsiz bo'lsa — ikkalasi rollback.

- Bir `row_id` uchun bir nechta kutilayotgan yozuv bo'lsa, klient push oldidan ularni oxirgi
  holatga siqishi (coalesce) MUMKIN; `op='delete'` doim g'olib.
- `SyncEngine` trigger'lari: app resume, internet qaytdi, foreground'da har 5 daqiqa, N yozuvdan
  keyin, pull-to-refresh.
- Push batch hajmi **≤ 200** o'zgarish.
- `attempts` eksponensial backoff uchun; `last_error` diagnostika uchun — unga shaxsiy ma'lumot
  yozilMAYDI.

### 3. Wire contract

#### `POST /sync/push`

```jsonc
// Request
{
  "device_id": "9f0e...",             // qurilma identifikatori
  "batch_id":  "1c1f...",             // UUIDv4, KLIENT generatsiya qiladi = idempotentlik kaliti
  "changes": [                         // <= 200 element, outbox seq tartibida
    {
      "entity":  "tasks",
      "row_id":  "6b1d...",            // UUIDv4, payload.id ga teng
      "op":      "upsert",             // "upsert" | "delete"
      "payload": { "id": "6b1d...", "updated_at": "2026-09-12T08:30:00Z", "...": "..." }
    }
  ]
}

// Response 200
{
  "batch_id": "1c1f...",
  "results": [
    { "row_id": "6b1d...", "entity": "tasks",      "status": "applied",  "server_version": 10427 },
    { "row_id": "77aa...", "entity": "habit_logs", "status": "conflict", "server_version": 10428,
      "server_row": { "...": "..." } },
    { "row_id": "88bb...", "entity": "tasks",      "status": "rejected",
      "reason": "updated_at_in_future" }
  ],
  "max_server_version": 10428
}
```

- Har o'zgarish uchun status **MUST** `applied | conflict | rejected` dan biri bo'lsin.
- `applied` — serverdagi holat klient yuborganidek (yoki merge qoidasi bo'yicha birlashtirilgan);
  `server_version` — yangi qiymat. Klient qatorga shu `server_version` ni yozadi va `dirty=0`.
- `conflict` — server merge natijasi klient yuborganidan farq qiladi; javobda `server_row`
  qaytadi va klient **MUST** uni lokal holatga yozsin (server natijasi g'olib), `dirty=0`.
- `rejected` — o'zgarish qabul qilinmadi. `reason` qiymatlari: `updated_at_in_future`,
  `unknown_entity`, `foreign_user`, `schema_invalid`. `updated_at_in_future` da klient qatorni
  `updated_at = now()` bilan qayta muhrlab outbox'ga qaytadan qo'yadi; qolgan sabablar uchun
  yozuv outbox'dan olib tashlanadi va loglanadi.
- **Idempotentlik:** server har `batch_id` ni `sync_batches(batch_id, user_id, device_id,
  response jsonb, created_at)` da saqlaydi. Xuddi shu `batch_id` bilan takroriy so'rov kelsa,
  server **saqlangan javobni qaytaradi va o'zgarishlarni QAYTA QO'LLAMAYDI**. `sync_batches`
  yozuvi o'zgarishlar bilan bitta DB tranzaksiyasida commit qilinadi.
- Batch 200 dan katta bo'lsa yoki `batch_id` UUIDv4 bo'lmasa → HTTP 400.

#### `GET /sync/pull?cursor=&limit=500`

```jsonc
// Response 200
{
  "rows": [
    { "entity": "tasks", "server_version": 10427,
      "row": { "id": "...", "deleted_at": null, "...": "..." } },
    { "entity": "tasks", "server_version": 10430,
      "row": { "id": "...", "deleted_at": "2026-09-10T12:00:00Z" } }
  ],
  "next_cursor": 10430,
  "has_more": false,
  "full_resync_required": false
}
```

- `server_version > cursor` bo'lgan qatorlar, `server_version ASC` tartibida; `limit` default va
  maksimum **500**.
- **Tombstone'lar ham qaytariladi** (`deleted_at != null`) — klient ularni lokal o'chirish uchun
  ishlatadi.
- `next_cursor` — oxirgi qaytarilgan `server_version`; klient uni `sync_state` da saqlaydi.
  `has_more=true` bo'lsa klient darhol keyingi sahifani so'raydi.
- **Yangi qurilma `cursor=0` dan boshlaydi** va butun holatni sahifama-sahifa oladi.
- Pull o'z qurilmasi yozuvlarini ham qaytaradi (echo); klient `server_version` bo'yicha idempotent
  qo'llaydi.

### 4. Conflict rules (normative)

Default: **row-level last-write-wins `updated_at` bo'yicha**. `updated_at` teng bo'lsa, serverda
allaqachon saqlangan holat g'olib. Istisnolar quyida; ular `apps/api/app/modules/sync/merge.py`
va klientdagi `core/sync/conflict.dart` da **bir xil** implementatsiya qilinishi shart.

| # | Doira | Qoida | Natija |
|---|---|---|---|
| 1 | Barcha sync jadvallari (default) | Row-level **LWW** `updated_at` bo'yicha | Kattaroq `updated_at` butun qatorni almashtiradi |
| 2 | `tasks.completed_at` | **max-wins** (NULL eng kichik) | Sync hech qachon vazifani "bajarilmagan" holatga qaytarMAYDI; qolgan maydonlar LWW |
| 3 | `habit_logs`, `prayer_logs`, `mood_logs`, `sleep_logs`, `health_logs` | Natural key **`(user_id, ref_id, date)`** (`id` emas) | Ikki qurilma bir kunga ikki yozuv yaratsa, ular bitta qatorga birlashtiriladi (saqlanuvchi `id` — `created_at` kichikrog'i) |
| 4 | 3-qatordagi jadvallarning **sonli additiv** maydonlari (suv ml, qadam, daqiqa) | **max-wins** | Additiv hisoblagich pasaymaydi; sonli bo'lmagan maydonlar LWW |
| 5 | `quran_progress.last_ayah_key` | **LWW** | Oxirgi o'qilgan joy oxirgi yozuv bo'yicha |
| 6 | `quran_progress.pages_read_total` | **max-wins** | Umumiy sahifa hisobi kamaymaydi |
| 7 | Har qanday qator, `updated_at > now() + 24h` | **`rejected`**, `reason: "updated_at_in_future"` | Klient `now()` bilan qayta muhrlaydi va qaytadan yuboradi |
| 8 | Soft delete | `deleted_at > updated_at` bo'lsa **o'chirish g'olib** | Tombstone qoladi; keyingi `upsert` faqat `updated_at > deleted_at` bo'lsa tiriltiradi |
| 9 | Noma'lum `entity`, yoki JWT `user_id` ga mos kelmagan qator | **`rejected`** | Klient yozuvni outbox'dan olib tashlaydi va xatoni loglaydi |

Merge natijasi klient yuborganidan farq qilsa, push javobi shu o'zgarish uchun `conflict`
statusini va `server_row` ni qaytaradi.

### 5. Retention and recovery

- **Tombstone retention: 90 kun.** `jobs/cleanup.py` 90 kundan eski, `deleted_at` qo'yilgan
  qatorlarni jismonan o'chiradi.
- Pull kursori shu oynadan eski bo'lsa (`cursor` allaqachon tozalangan `server_version`
  diapazonida), server **MUST** javobda **`full_resync_required: true`** qaytarsin va `rows` ni
  bo'sh qoldirsin. Klient bu signalni ko'rganda serverdan kelgan lokal holatni tashlab, `cursor=0`
  dan to'liq resync qiladi; **push qilinmagan outbox yozuvlari saqlanadi** va resync tugagach
  yuboriladi.
- **`row_history` — 30 kun.** Server har qabul qilingan o'zgarishning oldingi holatini
  `row_history(entity, row_id, user_id, before jsonb, after jsonb, server_version, device_id,
  created_at)` ga yozadi. Bu **faqat support orqali qo'lda tiklash** uchun; klient uni o'qimaydi,
  MVP da avtomatik rollback yo'q.

### 6. Out of scope (MVP da yo'q)

- Push batch > 200 o'zgarish — server 400 qaytaradi.
- **Field-level merge yo'q** (2, 4, 6-qatorlardagi aniq maydonlardan tashqari); qolgan hamma joyda
  qator butunligicha almashtiriladi.
- **CRDT yo'q**, operatsion transformatsiya yo'q, real-time (WebSocket) sync kanali yo'q.
- Faqat onlayn ma'lumotlar (auth, avatar, AI chat/planner/reschedule/recs/memory, server
  statistika, admin) bu protokoldan **o'tmaydi**.
- Faqat lokal ma'lumotlar (xom `dw_sessions`, `scrolling_events`, notification engagement log,
  AI javob keshi) **hech qachon yuklanmaydi**; DW dan faqat kunlik agregat chiqadi (ADR-0003).
- Qurilmalar aro ephemer holat ("oxirgi ko'rilgan ekran") sync qilinmaydi.

## Consequences

- Klient offline to'liq ishlaydi; internet paydo bo'lganda outbox `seq` tartibida yuboriladi.
- `batch_id` idempotentligi tarmoq uzilganda takroriy push'ni xavfsiz qiladi — "duplikat vazifa"
  sinfi butunlay yopiladi.
- `server_version` yagona manba bo'lgani uchun qurilma soatining noto'g'riligi kursorga ta'sir
  qilmaydi (faqat merge'ga, 7-qoida bilan cheklangan).
- Merge deterministik → 2-bosqich DoD dagi "konflikt matritsasi avtomatik test" (ikki in-memory
  Drift klient + test API) yozilishi mumkin.
- `sync_batches` va `row_history` jadvallari o'sadi; ikkalasi `cleanup` job bilan cheklanadi.
- **Open question:** reja `sync_batches` saqlash muddatini aytmaydi. Bu yerda tanlangan qiymat —
  **7 kun**, so'ng `cleanup` o'chiradi (klient retry oynasidan ancha uzun).
- **Open question:** reja push javobida `conflict` holatida server qatori qaytishini talab
  qilmaydi; `server_row` shu yerda qo'shildi, aks holda klient darhol pull qilishga majbur bo'lardi.
- **Open question:** reja 3-qoidadagi `ref_id` semantikasini jadval-bajadval belgilamaydi
  (`habit_id`, prayer nomi va h.k.); har jadval o'z `ref_id` ma'nosini migratsiyada hujjatlashi shart.
- **Open question:** reja `rejected` sabablari ro'yxatini bermaydi; yuqoridagi to'rtta qiymat shu
  ADR da belgilandi.

## Alternatives considered

| Variant | Nega rad etildi |
|---|---|
| **CRDT (Automerge/Yjs)** | Har maydon uchun metadata, katta lokal hajm, solo dev uchun debug qiyin; KUNIM entity'lari amalda "bitta foydalanuvchi, bir vaqtda bitta qurilma" xarakterida. |
| **Field-level merge hamma joyda** | Merge matritsasi portlaydi, testlash qimmat; real ziddiyatlar faqat 2/4/6-qatorlardagi maydonlarda uchraydi. |
| **Server-generated `id`** | Offline yaratilgan qator darhol lokal bog'lanishlarga (`task_id`, `habit_id`) kerak; server ID kutish offline-first ni buzadi. |
| **`updated_at` ni kursor sifatida ishlatish** | Qurilma soati ishonchsiz; monoton bo'lmagan kursor yozuv yo'qotishiga olib keladi — shuning uchun `server_version` majburiy. |
| **Real-time WebSocket sync** | MVP uchun batareya va murakkablik; 5 daqiqalik poll + silent data-push yetarli. |
| **Hard delete + alohida o'chirish jurnali** | Tombstone'siz qurilma o'chirilgan qatorni "yangi" deb qayta yaratadi. |

## Revisit when

1. Konflikt matritsasi testida (2-bosqich) LWW bilan tuzatib bo'lmaydigan ma'lumot yo'qotish
   ssenariysi topilsa;
2. Foydalanuvchilarning ≥ 1% ida bitta sync sikli doimiy 200 dan ortiq o'zgarish hosil qilsa
   (batch limiti yoki delta format qayta ko'riladi);
3. Family Account (2-bosqich) bir qatorni **bir nechta foydalanuvchi** tahrir qiladigan holatni
   kiritsa — per-user `server_version` va LWW yetarli bo'lmaydi;
4. Pull p95 kechikishi 500 qatorli sahifada > 1 s bo'lsa;
5. `full_resync_required` oyiga faol qurilmalarning 1% dan ko'pida ishga tushsa (tombstone muddati
   uzaytiriladi).
